## Critical review of the “comments to your critique” (what still doesn’t line up with this repo)

You fixed several real issues (Poppler removal, explicitly separating private graph data, and acknowledging “high‑confidence wrongness”). But the revised writeup still has a few **repo‑incorrect assumptions** and a couple of **new risks / hidden engineering traps**.

### 1) **PrivacyController is conceptually good—but currently “paper armor”**

* In the repo as‑is, there is **no central enforcement layer** (no middleware, no shared “data type” routing, no consent store).
* If you add a `PrivacyController` but don’t **wire it into the actual choke points** (PDF profiling, URL profiling persistence, Notion push, any future sync), it creates a **false sense of safety**.
* “Encryption for private fields” is a **big lift** in SQLite without SQLCipher (and adds ops complexity). For a small fund team, the “lowest-debt” privacy control is **separation of stores + safe defaults**.

### 2) **Your ClaimStore integration snippet is not repo-correct**

In this repo, `ClaimStore.save_extraction()` is:

```py
save_extraction(
  entity_key, extractor_name, extractor_version,
  predicate_hint, raw_text, source_url,
  source_snippet=None, start_offset=None, end_offset=None
)
```

Not:

* `content=...`
* `metadata=...`
* `extraction_ids=[...]` on `save_claim` is correct, but **`is_private=` is not supported**.

So the PDF profiler spec must follow the **exact ClaimStore API** to avoid a mismatch.

### 3) **“SQL migrations/*.sql” is not how this repo migrates**

This repo uses `storage/signal_store.py`’s `MIGRATIONS` dict + `CURRENT_SCHEMA_VERSION`.
So your `migrations/002_finance_predicates.sql` plan won’t be discoverable by the existing CLI/schema tooling.

### 4) **TTL cache “auto deletes after 30 days” is not automatic**

SQLite will not expire rows by itself.
If you want TTL, you need:

* a `expires_at` column **and**
* an explicit cleanup call (on command start, on a cron, or in `run_pipeline.py` maintenance commands).

### 5) **WarmIntroEnhancer uses fields the repo does not expose**

Investor matching results do **not** include `partner_email`. They include `investor_id`, `investor_name`, and (from the `investors` table) things like `website_domain`. So warm intro logic must key off **domain / investor_id**, not partner email.

### 6) **Curated discovery cannot rely on a single “curated_discovery” signal and expect the gate to push**

`verification_gate_v2` gives unknown signal types a low default weight (0.05). A single new signal type will almost always route to **HOLD**, not “Source/Tracking”.
To be effective *and* repo-aligned, curated discovery should:

* use “curated discovery” as a **seed**
* then immediately run the existing multi-source enrichment/verification pattern (e.g., `SignalOrchestrator` collectors) to generate known signal types.

### 3.4 Scoring (make it deterministic + explainable)

Replace the vague `recency_decay` variable with a concrete function:

* `days_since_last = (now - last_interaction).days`
* `recency_score = max(0.0, 1.0 - min(days_since_last, 365) / 365)`

Then:

```
strength = clamp01(
  0.50 * sigmoid(intro_count) +
  0.35 * reply_rate +
  0.15 * recency_score
)
```
